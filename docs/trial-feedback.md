## 一次反馈所需的最小信息

| 字段 | 填写内容 |
| --- | --- |
| 匿名案例号、日期 | 自定编号，不填真实身份 |
| 环境 | OS、DSH 版本、ACE 安装版本和页面 build 版本 |
| 调用 | provider/model、模式、自动或手动触发 |
| 上下文 | 大致轮数/长度，是否开启 ledger；无需贴私聊 |
| 现象 | 无卡、未校核卡、正常卡、错误；保留可公开的错误码 |
| 时间 | 用户实际等待；若可取得，响应中的 latencyMs 与 timings.movesMs/reviewMs/totalMs |
| 复现 | 同一对话是否稳定出现，短对话是否也慢 |
| 结果 | 重试或升级后是否解决；未测就写未测 |

`movesMs` 包含生成与重试耗时；`reviewMs` 是校核耗时；`totalMs`
包含流水线内其他工作。浏览器计时还可能包含历史加载及网络等待。
失败请求可能没有 timings，缺失不能填 0。截图里的等待文案不证明后端阶段。
清空上下文只能帮助定位；原有长对话复测通过后，才能说该场景已解决。

## 提速与质量对照

在同模型、同模式、同一份经脱敏的输入和相同配置下比较两个版本。
记录每次运行，建议每版本至少 3 次；保留超时、空卡和失败，不只挑最快一次。
记录中位等待时间、范围、出卡次数、未校核次数和错误次数。小样本仅用于排查。

请用户分别回答：

1. 这张卡说的是什么？请用自己的话复述。
2. 能否独立举出另一个同机制的例子？
3. 是否出现原先没想到且有用的方向？
4. 会不会采用？需要改多少？若实际交给 AI 执行，结果如何？

采用不等于能力提升，能复述也不等于远迁移。各项分别记录；
没有测试的维度留空，失败和负面反馈照样保留。

## 发布前检查

- `npm test`：包括校核通过、内容拒绝、真实计时器触发的模拟超时、
  警告可见、取消和 Tab 只填草稿。
- `npm pack --dry-run`：检查发布清单；包隔离导入测试通过。
- 在隔离 profile 安装目标 tarball：核对包、health、页面 build 版本。
- 一次真实模型出卡与一次原长对话复测；记录耗时和结果，不以 fixture 替代。
- 验证禁用/回滚后 composer 可用。
- 同步双语说明、CHANGELOG、安装版本和 Release 资产。main 推送不等于
  Release 已发布，已发布也不等于试用者已安装。

本表不会自动收集数据，也不会向社群发送消息。
